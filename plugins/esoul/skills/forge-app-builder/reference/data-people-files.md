# Data, people, files — the platform's capabilities an app declares and gets for free

You never write a migration, an ORM, a `WHERE userId = …`, an auth check, a token refresh or a
Drive client. You declare; the platform generates, scopes, gates and holds. This page is the
declarations and the traps behind each.

## 1. Your own tables — `db`

For what does not belong on the fold: per-person, unbounded, must never revert on a scrub.

```json
"db": {
  "Ticket": {
    "owner": "creator",
    "fields": { "status": "string=open", "subject": "string", "detail": "text", "article": "ref:Article?", "tags": "string[]" },
    "indexes": [["status"], ["createdAt"], { "fields": ["tags"], "kind": "contains" }, { "fields": ["subject"], "kind": "text" }],
    "unique": [["subject"]],
    "rules": {
      "read":   ["creator", "agent", "supervisor"],
      "create": { "roles": ["requester", "agent"], "requires": "account" },
      "update": { "roles": ["agent", "supervisor"], "creatorMay": ["detail"] },
      "delete": ["supervisor"]
    }
  },
  "ContactDetails": { "scope": "user", "sealed": ["phone"], "fields": { "label": "string", "phone": "string" } }
}
```

- **Types** `string text int float boolean datetime json ref:Model`; `?` optional, `=v` default,
  `[]` list. Platform columns (`id workspaceId nodeId ownerId createdBy createdAt updatedAt
  deletedAt`) are added; never declare them.
- **Scope**: `instance` (default: this app instance's rows) · `workspace` (shared across
  instances) · `user` (one person's, across instances — cursors, preferences).
- **`owner: "creator"`** — the row belongs to whoever made it (`creator` in rules), across every
  id that person has acted under (an anonymous row stays theirs after sign-in).
- **`sealed`** — encrypted at rest; readable by the row's owner and your own internal code;
  null for anyone else. Where a pasted secret or a phone number lives.
- **Rules** name principals: `anyone`, `creator`, a role from your vocabulary, `apps` (bound
  apps), or a scoped role `{ "role": "customer", "where": { "customer": "viewer.customer" } }`
  (rows carrying the number the grant holds; a missing attribute grants nothing). Compiled at
  build; the SAME artefact drives the in-memory client your tests use, Prisma in production,
  and the box. A rule naming an undeclared role fails the build with the path.
- **Indexes are the question wall**: `orderBy` and `where` are allowed ONLY on indexed fields;
  `contains` (a GIN index) answers `{ tags: { has: "gifts" } }` on a list; `text` answers
  `{ subject: { contains: "grey" } }` case-insensitively. Asking the wrong shape is refused as
  `invalid` with the right one named — an empty result would look like an empty shelf.
- **Migrations are additive** on install: new tables/columns/indexes apply; a type change or a
  required column without a default is REFUSED with the column named. Uninstall keeps tables.

```ts
const db = await pluginDb<HelpdeskDb>(ctx);            // type from ./.esoul/db (generated by check_app; pull it)
await db.ticket.findMany({ where: { status: "open", tags: { has: dept } }, orderBy: { createdAt: "desc" }, take: 24, cursor: after ? { id: after } : undefined });
await db.ticket.aggregate({ where: { status: "open" }, _count: true });                  // count in the database, never page-and-add
const order = await db.$transaction(async (tx) => { const o = await tx.order.create({ data }); await tx.cartLine.deleteMany(); return o; });   // one breath or neither
```
**Paging**: `take` is 200 at most; `cursor: { id }` returns the rows AFTER that row — never add
Prisma's `skip: 1` (refused). Pages end in `id`, so ties on `orderBy` cannot repeat or vanish. To
read a whole table, loop until a page is short; to count or sum, ask `count`/`aggregate`.

The surface: `findMany findFirst findUnique count aggregate groupBy create createMany update
updateMany upsert delete deleteMany $transaction`. `ctx.viewer` is already inside the client —
there is no argument that reads someone else's rows; naming `workspaceId`/`nodeId`/`ownerId`
in a query is refused. **A call into another app is outside your transaction** (hold → write →
release on failure yourself). A json column answers about one row; sales are a table (the price
at the time).

## 2. People — viewer, roles, access

Every seam receives a `viewer`: UI `useViewer()`, server `ctx.viewer`, tasks `ctx.kickedBy`.
```
viewer.kind      "owner" | "member" | "visitor" | "anonymous" | "agent" | "internal"
viewer.userId    the account or null · viewer.role  YOUR word · viewer.canWrite · viewer.signedIn (a guess)
```
An agent gains nothing (it is whoever it acts for); `internal` is your own server code (rules do
not apply, scope does). An app cannot forge or widen a viewer.

**Roles are your vocabulary**, mapped from the platform's kinds; the workspace owner may
override per person, per app, in the sharing UI (with your `describe` texts):
```json
"roles": { "vocabulary": ["requester", "agent", "supervisor"],
  "default": { "owner": "supervisor", "member-edit": "agent", "member-readonly": "agent", "visitor": "requester", "anonymous": "requester", "agent": "inherit" },
  "describe": { "requester": "raises tickets and sees their own", "agent": "answers every ticket", "supervisor": "everything" },
  "attributes": { "customer": "int" } }
```
`inherit` = an agent takes its person's role; `none` = no word for that kind (no rule can match
them). A role is a WORD, never a permission — a read-only member you call `agent` still cannot
write. `attributes` type what a grant may carry (an admin links customer 143 to an email); rules
scope by `viewer.<attr>` — for rows written on someone's BEHALF (a machine, an import).

**Access levels** on every op / route / kickable task — `write` (default: owner + editing
members) · `read` (anyone who can SEE the workspace, incl. read-only members — NOT outsiders) ·
`public` (share-link holders, no workspace access) · `public` + `requires: "account"` (must sign
in → `login-required` + `signInPath`; `useSignInWall()` renders the wall) · `token` (routes: a
machine). Refusal codes: `forbidden` 403 · `login-required` 401 · `not-bound` 409 · `rate-limited`
429 · `invalid` 400; in a box each carries a `detail` written for you.

**Never gate a read on `viewer.signedIn`** — it is this page's guess and disagrees with the
session on shared links (a real shop showed a signed-in person an empty basket and a wall while
the server held their order). Attempt the call; let the refusal answer:
```tsx
const wall = useSignInWall();
wall.ask<Cart>(() => callPluginOp(PLUGIN_ID, "view-cart", nodeId)).then((c) => c && setCart(c));   // null + the wall when the SERVER says no account
```
`viewerProfile(ctx.viewer)` (server) → `{ userId, email, name, picture } | null` — the CALLER's own
details only; use it to pre-fill, never to look someone up.

**Test it as five people**: `fakeViewer("visitor", { userId: "u_ada", role: "requester" })` +
`memoryDb(manifest)` + `runOp(pluginServer, op, { viewer, args, db: db.as(viewer) })`; the
assertion that matters is that visitor-b's count of visitor-a's rows is **0**. In the box, VIEW
AS (`look_at_app` / `drive_app` with `viewer: "visitor-b"`, or `visitor-a?grant=customer&customer=143`)
photographs the screen each person gets — the one screen an author never sees otherwise. Under
the hood VIEW AS is `previewPersona()` (`esoul-sdk`): a preview writes the pretend person onto
the window and every UI call carries it, so the server sees the same person the screen shows;
outside a preview it is `null` and nothing is sent — never branch on it in app logic.

**Roles the owner composes at runtime.** The vocabulary above is fixed at build; an owner may
also compose a narrower word later — a "packer" who sees only orders being prepared — without a
redeploy. The manifest declares the ENVELOPE such a role may narrow within, and the platform
refuses any definition that would widen it:
```json
"roles": { "…": "…",
  "custom": { "models": { "Order": { "where": ["status"], "hide": ["note"], "update": { "fields": ["note"], "transitions": "status" } } },
              "ops": ["set-order-status", "fulfil-order"] } }
```
Server API (`esoul-sdk/server`), owner-only, every write appended to the app's own timeline:
`defineAppRole(ctx, def)` composes or removes a word · `setAppRole(ctx, { email, role, attrs? })`
gives one person one app's access (`role: ""` revokes; `attrs` typed by `roles.attributes`) ·
`listAppRoles(ctx)` → everyone with a grant here and the words that exist · `removeAppRole`.
A composed role reaches `ctx.viewer.customRole` / `ctx.viewer.custom` and the SAME rule engine
narrows by it — nothing an app writes decides access. The full walk-through, with the packer, is
`docs/13-people-and-access.md` → "Roles the owner composes" and "Giving one person access to
one app" (how to read the SDK docs: `SKILL.md` → "Reading the SDK's own docs").

## 3. Accounts — a service with a login

**Read `accounts.md`.** In short: the person's account at Google, Microsoft (Outlook, OneNote,
OneDrive), any OAuth 2.0 provider, or a pasted API key is a **credential slot** in plugin.json
(`family: "google" | "oauth2" | "apiKey"`). The person connects it once in Account settings
(→ Google, or → Accounts) and assigns it to the app; your code calls
`credentials(ctx).slot(name).fetch(url)` (in a task `ctx.credentials(name)`) and never holds the
token, key or client secret — the platform adds it and sends it only to the slot's declared
`hosts` (Google: the endpoints its scopes reach). UI: `useCredential` + `<ConnectAccount/>`. In a
box a Google slot talks to a simulated Gmail; an `oauth2` / `apiKey` slot answers `not_bound`, so
test those calls with `fakeCredentials`. The older `connections` +
`getPluginConnectionCredentials` hand the token to your code — never for new work.

**Model calls** are not a connection: declare `llm` and call `llm(ctx)` / `ctx.llm` (billed to
the owner within the manifest's budget; a scripted model in the box; `docs/19`). Never import a
model provider's SDK — the import wall refuses it.

## 4. Files — the workspace's files and Google Drive

```json
"fileSources": { "workspace": "read", "providers": ["google-drive"], "write": ["google-drive"] }
```
Absent = no file access. Every `write` key must also be in `providers`, or a write answers
`not_declared` (in the Forge exactly as after install). Identity is `sourceId` + an opaque `ref`
— **remember a folder by its `ref` in the fold (an event), show its `path`**; a rename does not
lose the place. Source ids: `workspace`, `google-drive`, `local:<mountId>`, `<provider>:<connectionId>`.

Server (`const files = await filesForOp(ctx)`): `sources()` · `list(sourceId, folderRef?, cursor?,
{ only, nameContains, orderBy, pageSize ≤ 1000 })` narrowed at the source · `listAll(…)` →
`{ entries, truncated }` (max 20,000) · `resolvePath(sourceId, "a/b/c")` → `{ found, entry,
chain, missing }` · `read(ref, { capBytes })` (25 MB default) · `readMany(refs, { as: "text" })`
(≤ 200; a failure stays in its own row) · `write({ sourceId, folderRef, name, bytes,
contentType })` (make or REPLACE by name — Drive keeps the same file id) · `readGrant({ sourceId,
ttlSeconds })` + `fileGrantUrl(grant, ref, { width? })` (signed expiring URLs, no session — for a
preview's `<img>` and for a machine's `curl`; one source of one workspace; 1 h default, 24 h max)
· `getUrl`, `saveWorkspaceFile`, `importToWorkspace`. Errors are typed (`FileSourceError.kind`:
`not_declared source_unavailable not_found too_large read_only disabled bad_ref`); a source that
cannot answer THROWS `source_unavailable`, never an empty list — show the message.

**Saving files, and lists of files.** Saves are idempotent (the same `key`, or the same bytes and
name, into the same folder is the same file — `deduped: true`; a clash becomes `"quote (2).pdf"`
unless `onConflict` says `skip`/`fail`), and every save appends `workspace/file_added`. A LIST of
files goes as one durable platform job the person watches in the tasks pane ("Saving 37 files to
Mail/Quotes — 12/37", Stop, Retry): `files.transfer({ requestKey, title, to: { sourceId:
"workspace", path: "Mail/Quotes" }, onConflict, items: [{ from: "google-drive:/Reports/q3.pdf" },
{ from: { sourceId, ref } }, { producer: "attachment", key }] })` → a `Transfer`;
`getTransfer(id)` / `listTransfers()`; UI `useTransfer(id)`; in a task `ctx.files`. Bytes your app
makes itself (a mail attachment, a render) come from a `fileProducers` entry in `server.ts`. A retry
leaves no residue. The whole contract is `docs/09-files.md` → "Moving a list of files".

Label files: `pairImagesWithLabels(entries)` from ONE listing is the single answer to "which
images are labelled"; `parseLabelMe` / `serializeLabelMe` / `labelFileNameFor` beside it.

UI (`esoul-sdk/react`): `useFileSources(workspaceId)`, `useFileSourceEntries(opts, loadMore)`,
`useFolderAutocomplete(workspaceId, sourceId, text)` → `{ suggestions, pathWith(entry),
resolve(), loading, error }` (do not write your own listing loop per keystroke), `useFileUrls`
→ `urlOf(ref, { width: 320 })` (Drive's own thumbnail, ~12 KB) / `urlOf(ref)`,
`usePluginWorkspaceFiles()`, `usePluginFileUpload()`, and `ImageLabeler` (the Explorer's polygon
editor: change `seedKey` per image AND when its labels finish loading; `onSave` throws the
sentence to show; the parent needs a height). Files work in a box through the box grant with no
board tab. **A write in a box is a real write** — prove `write` on a scratch folder the person
names, never on their dataset. Test ops with `memoryFiles(tree)` from `esoul-sdk/testing`.

**Contributing a source of your own — `fileProviders`.** An app with a connection to a service
that holds files (a DAM, an S3 bucket, a scanner) can CONTRIBUTE a mount: `"fileProviders":
[{ "key": "acme-dam", "connectionKey": "acme", … }]` in the manifest, implemented as
`pluginServer.fileProviders[key]` in `server.ts` — one mount per ACTIVE connection, listed in
the Explorer beside Drive, readable by other apps that name your key in their `providers`. The
key is globally unique across installed apps (host keys are reserved; the sync refuses a
collision). In a box, `pluginFiles(ctx)` is the same files door on the box grant — what
`filesForOp` gives an op after install. Both are in `docs/09-files.md`.

## 5. Public viewers and sharing

An app on a public share (`publicSharing` on the schema): `policy: "never"` for private data, or
a `redactState(state)` that is the ONLY wall between the app and the internet — fail closed. A
`publicSafe` tool never writes and never leaks; a route checks `ctx.canWrite`; a `public` op is
rate-limited by the platform. Design for the reader who is not the owner: their face follows the
same events.

## 6. Pictures and charts

`generateAppImage(ctx, { name, prompt, style, shape })` → an https URL for your row — ONE style
for every picture in the app; costs money, so behind an owner-only op; refused in a box on
purpose. Draw the empty case first (an aspect box with an inline SVG pattern), so nothing moves
when a picture arrives. `chartSvg(spec)` (pure; glyph outlines, impossible-value rails, gaps) for
the screen and `renderChartImage(ctx, { name, svg })` for a tool's answer — a stored PNG URL
installed, `base64` in a box (put the chart on a page of the app and say so; never hand base64
to a chat).
